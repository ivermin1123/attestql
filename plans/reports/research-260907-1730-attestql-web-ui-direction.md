## 1. Summary

**Build a static evidence viewer that the CLI itself renders, and make attestql.com that renderer
run over the audits this repository has already published.** One `attestql report <audit-dir>`
command turns the four JSON files a run writes into linkable HTML pages; the site is the same
pages for the five published runs plus an index. No server, no accounts, no execution of a
stranger's SQL, no second implementation of the renderer in JavaScript.

What makes it worth looking at is not decoration. It is that every question page tells one
story in a fixed order (question, the two statements, where their rows differ, what the benchmark
would have scored, how to run it again), that every cell carries its declared type so a
disagreement that lives only in the type is visible at all, and that the page never says "the
gold is wrong". The tool's principle is the interface's principle: show, never judge.

Proposed as a fifth phase, after the owner asked for it to be costed: an in-browser drop zone
for private audits and in-browser hash verification, both through Pyodide so the renderer and
the serializer stay one implementation. Measured 2026-09-07: about 6.3 MB compressed to first
render, loaded on demand and cached, on the viewer page only. Deferred: cross-run comparison and
a paste-two-statements playground (needs a server and a security boundary).

## 2. What the data affords (OBSERVED)

A run writes, per question directory `audit/q<id>/`:

| File | Format string | Holds |
| --- | --- | --- |
| `counterexample.json` | `attestql/audit/counterexample/2` | question text and hint, both statements, replay rule, verdict with mismatched preconditions, BIRD's EX reading, the test-suite reading, the mechanism class, both results as a 25-row preview per side (`rows_shown` against `row_count`, typed cells, `truncated` flag, the hash over every row), each side's own ordering, the canonical ordering, `differing_rows` split into in-gold-not-in-second and in-second-not-in-gold with `rows_shown_per_side`, both result hashes, backend identity, fixture, run id |
| `evidence-gold.json`, `evidence-second.json` | evidence record | executed SQL, role, backend identity, execution limits, session settings, serialization descriptor, canonical ordering, the result whole (every row, per-column declared type), fixture hash, result hash, record hash, rerun instruction |
| `smells.json` | `attestql/audit/smells/2` | one entry per probe: `name`, `fired`, `applicable`, `evidence`, `counterexample_rows` (at most 10), and a `reading` line stating a smell is a heuristic |
| `summary.json` (run root) | `attestql/audit/summary/2` | counts by verdict and smell, `credited_but_not_equal` by mechanism and by test-suite reading, errors and timeouts by side, fixture measurement, shuffle state, session settings, parser, question set and prediction digests and origins |

Source: `src/attestql/audit/compare.py` (`counterexample_json`, `write_comparison`),
`src/attestql/audit/smells.py` (`smells_json`), `src/attestql/audit/cli.py` (`_summary_json`,
`_write_question`). A gold-only question writes the gold record and the smells, no counterexample.

DERIVED: every screen below is a projection of these files, so the renderer needs no database
and no network, and a page can always link to the exact JSON it was rendered from.

What does not exist yet (OBSERVED): the published gold-only runs under `plans/reports/` hold only
`summary.json` and `stdout.txt`; the prediction-mode and BIRD dev directories hold aggregates,
the hand classification and a few examples. Per-question directories for the rows the site would
show have to be regenerated by running the CLI again (plan phase 4).

## 3. Audience and the one job per screen

| Screen | Who | The one thing they must see first |
| --- | --- | --- |
| Question page | a benchmark maintainer reading an upstream report; a researcher checking one of their predictions | the differing rows, with the verdict and the rule that produced it one glance above |
| Run page | someone deciding whether to trust a run | the counts, and what the run was made of (digests, origins, server, parser) |
| Landing | a visitor from an issue, a post, or a search | one sentence of what this is, the headline finding, and the ten-minute command |
| Record section | a second person re-running one execution | the rerun command and the preconditions it must hold |

Ranking rule from the design reference: visual weight reproduces this order. The verdict strip
and the differing rows get the size and contrast; the record, the settings and the hashes are
dense and quiet, present and secondary.

## 4. What comparable interfaces do (reference)

- **Recce** (dbt data validation, OBSERVED from its docs and blog): matches rows by primary key,
  compares column values, and offers a change-only view that returns only rows with a difference.
  Lesson: differing rows first, full results on demand. AttestQL has no primary key; its unit is
  the rendered row and its multiplicity, which the UI must show as a count column.
- **Datafold data-diff** (OBSERVED: repository archived 2024-05-17, read-only; the company moved
  to its cloud product). Lesson: the open-source row-diff niche has been vacated, which is one
  more reason the renderer belongs in the CLI and not in a hosted service.
- **GitHub pull request diff** (PRIOR): split and unified views, per-token highlighting inside a
  changed line. Lesson: for the two SQL statements, highlight the differing tokens, do not make
  the reader find `::numeric` by eye.
- **Hugging Face dataset viewer** (PRIOR): the column header carries the type. Lesson: type in the
  header, and a per-cell tag only where a cell's type differs from its column's.
- **Distill and The Pudding** (OBSERVED from the fetched pages): the "martini glass" structure,
  an author-guided stem then reader-driven exploration; progressive disclosure, overview first;
  interaction that changes what the reader sees, not decoration. Lesson: the question page is a
  fixed narrative first and an explorer second.
- **Enterprise table guides** (OBSERVED, Setproduct and Pencil and Paper): align each type the way
  the eye expects, numbers right and tabular, badges only for states a reader scans for.

## 5. Design direction

**Register.** A lab notebook or a court exhibit: calm, dense, exact, with editorial confidence.
Not a marketing page, not a dashboard. The test from the design reference: swap in another
product's copy and the design should stop fitting; here the typed cells, the verdict strip and
the rerun block belong to this tool and to nothing else.

**Tokens.** One accent, one warning tone, a warm neutral ramp, two type families, one spacing
scale. Exact values are in `plans/260907-1730-attestql-web-ui/design-spec.md`. Constraints that
matter more than the values: diff colours are semantic and must not reuse the accent; there is no
green tick anywhere, because a green tick says "correct" and the tool never says that; colour is
never the only carrier of a difference (a label column and a glyph carry it too).

**Typography.** IBM Plex Sans for text and controls, IBM Plex Mono for SQL, cells, hashes and
commands; both self-hosted woff2 under the OFL, no third-party font request. Body 16px at line
height 1.5, measure 60 to 75 characters for prose; tables and SQL escape the measure inside their
own horizontal scroll region.

**Tables.** Header carries column name and declared type. Numeric cells right-aligned with tabular
figures; NULL rendered as the serializer renders it and styled as a state, not as text; row
multiplicity as a leading count column when any row repeats. Differing rows first, labelled
"in gold, not in second" and "in second, not in gold" with a glyph and a tint. Full results
collapsed under a count ("all 13 rows"), rendered to a cap with a link to the JSON for the rest.

**States, designed rather than inherited.** EQUAL; NOT_EQUAL by mechanism (multiplicity, type,
order, truncation, other); ERROR by side with the engine's message; GOLD-ONLY; a probe that is
`fired`, quiet, or `applicable: false` (not covered, or the shuffle not run); a truncated result;
a timed-out statement; a fixture with missing or unreadable tables. Each has copy and a mark.

**Dark mode** as a re-decision: borders replace shadows, tints re-tuned for contrast, computed not
eyeballed. **Print** works, because a page is an exhibit someone may attach to a report.

**Copy rules.** The page uses the tool's own vocabulary and its `reading` strings verbatim where
the JSON carries them. Forbidden on any page: "correct", "wrong gold", "the gold is wrong",
"score", "accuracy". A test greps the templates for them.

## 6. Motion: only where it communicates

Personality: Corporate. Signature easing `cubic-bezier(0.2, 0, 0, 1)`; duration palette 120,
240 and 400 ms; one entrance pattern, opacity plus an 8px rise. Four places motion earns a
place, nowhere else:

1. Differing rows reveal with a 30 ms stagger capped at 300 ms total, so the eye reads them as a
   set arriving, not a table popping in.
2. Hovering or focusing the mechanism chip highlights the tokens that differ in the two
   statements (120 ms).
3. The sticky verdict strip condenses on scroll (240 ms) so verdict and rule stay in view while
   the reader is deep in the rows.
4. Later, when in-browser hash verification exists: a checkmark draw on match (300 ms), and no
   colour change on mismatch beyond the warning tone.

`prefers-reduced-motion` reduces every one of these to an opacity change. No parallax, no
looping ambient motion, no animated numbers on the landing page.

## 7. Technology options

| Option | DRY with the CLI | Linkable per-row pages | Toolchain added | Fit for one Python maintainer |
| --- | --- | --- | --- | --- |
| A. Python renderer in the CLI (Jinja2 templates, one CSS file, one small JS file), site built by running it | one renderer, three uses | yes, static HTML | Jinja2 (BSD) | best |
| B. Astro or Eleventy reading the JSON at build time | second renderer in JavaScript | yes | Node build, second language | poor |
| C. Client-side JavaScript viewer with a drop zone | second renderer | only with hash routes, not crawlable | none | poor for DRY, good for private audits |
| D. Pyodide running the Python renderer in the browser, for a private-audit drop zone | one renderer | no, unless combined with A | Pyodide 314.0.6: 3.44 MB runtime plus 2.51 MB standard library, brotli, measured; Jinja2 in its lock; `tzdata` must be bundled; lazy | good as an addition to A (phase 5, proposed); hash verification does not need it, the CLI recomputes at render time |

Chosen: **A**, with D proposed as phase 5 for the drop zone and hash verification without a
second implementation. B is rejected for the second language; C for the second renderer. The
import audit that makes D possible: the evidence and serialization modules import only the
standard library; the engine bindings live under `attestql.audit` alone. Until phase 5 lands, a
person with a private audit views it by running `attestql report` locally.

Hosting: Cloudflare Pages. attestql.com is live on project `attestql` (main session, 18:05),
deployed by hand with wrangler from outside the repository, serving `site/index.html`. The built
site goes to `build/site/` from `tools/site/` and deploys to a preview project `attestql-ui`;
moving attestql.com to it is the owner's step, and the GitHub Actions deployment the owner
prefers is added at that switch. Pages' per-file limit is 25 MiB, which the Pyodide runtime
files of phase 5 stay under.

## 8. Page map

```text
/                                  landing: one sentence, the finding, the command, benchmark index
/runs/<benchmark>/                 the CLI runs of one benchmark (one per prediction file)
/runs/<benchmark>/<run>/           run page from that run's summary.json, question index, filters
/runs/<benchmark>/<run>/q<id>/     question page: story first, then results, smells, records, rerun
/runs/<benchmark>/<run>/q<id>/*.json  the exact files the page was rendered from
/method/                           the rules in one page: R-ORD and R-SET, the serializer, the probes
```

Benchmarks for the first publish: `bird-dev-sqlite` (one run), `minidev-sqlite` (nine runs),
`minidev-pg-gold-only` (two, the zip and the Hugging Face file), `minidev-pg` (nine). A run is
one CLI run because the audit writes one second statement per question per run. Only questions
the site is about get a page (credited-but-NOT_EQUAL, fired-probe golds, hand-classified rows,
the unjust-zero and unjust-one cases); ERROR questions are listed from the summary; the run page
lists every question; full runs are release assets.

## 9. Risks

- **Page count and size.** `counterexample.json` previews 25 rows per side; the two evidence
  records hold every row, so a question directory can be megabytes, and Cloudflare Pages holds
  20,000 files per site on the Free plan. Pages exist only for the questions the site is about
  (a few hundred), full runs are release assets, and the budgets come from a dry run of the
  selection script. Reviewed 2026-09-07: `plans/reports/review-260907-1806-web-ui-plan-red-team.md`.
- **Copy that judges.** The easiest way to make a page "interesting" is to say the gold is wrong.
  Mitigation: the forbidden-phrase test and the hand classification labelled as a human reading,
  separate from the verdict.
- **Generated look.** Template output tends to the average. Mitigation: the design spec fixes
  tokens before markup; phase 2 renders at three widths with the longest real content and checks
  contrast and measure by computation, not by eye.
- **Regeneration cost.** The PostgreSQL runs need the container and the Mini-Dev dump; the SQLite
  runs need only files. Phase 4 orders them SQLite first.
- **Accounts.** Everything outward (Pages, DNS, the repository workflow) runs under the personal
  identity; the plan names it at each step.
- **Two sessions on `main`.** The main session owns the checkout at `Desktop/code/attestql`,
  `README.md` and `site/index.html`, and asked (18:05) that this work live in its own worktree,
  which it does (`~/orca/workspaces/attestql/web-ui`, branch `web-ui` under the owner's
  handle). Phase 3
  touches neither file and deploys only to a preview project.
